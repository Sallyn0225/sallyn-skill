# 实测教训

SKILL.md 里每条规则背后的案例与推理。主代理在对应步骤遇到拿不准的情况时来这里查,平时不必通读。

## 路径:给子代理写路径一律用正斜杠

Windows 反斜杠路径在 prompt 里会被当成转义吃掉——`...\_context\research\01.md` 里的 `\_` 会变成 `_`,子代理于是在工作区**旁边**建了个 `<stem>_context/` 目录写进去,而且它自己毫不知情、照样回报"已写入"。写成 `E:/.../<stem>/_context/research/01.md` 就没这个问题。派发后顺手 `ls` 一下目标目录确认文件真的落在那里。

## 第 0 步:上游 ASR 的 JSON 能不能省掉整平

若能拿到上游 ASR 的转录 JSON(带 word 级时间戳),优先让用户用上游脚本本地重渲染出"一句一条"的 SRT 作为输入,**不产生二次计费**,质量也比启发式整平可靠(有真实词边界和更细的时间戳)。例如 ElevenLabs:

```
uv run python <asr仓库>/scripts/render_from_json.py <out.json> -f srt -o <name>_oneline \
    --max-line-width 999 --max-lines 1
```

但这条路常常走不通:多数 ASR 脚本只落 SRT 不存 JSON(如 DashScope Fun-ASR 的 `transcribe_to_srt.py`),转录 URL 也会过期;而且只有句级时间戳的 JSON 重渲染**解决不了粘连**——它的 sentence 边界就是 SRT 的条目边界,重渲染出来还是那几条(mossland-asr 的 `.json` 就是这样:`segments` 只有 `start`/`end`/`text`/`speaker`,与 SRT 一一对应,拿它重渲染毫无收益)。拿不到、或重渲染后 `stats` 仍报 `split: NEEDED`,就直接进第 1 步,由第 3 步整平。两条路径在第 3 步汇合,后续完全一致。

## 第 0 步:「又长又挤」的第三种情况不是失形

一个条目超出宽度阈值,可能只是因为它本来就是一个长句。判据是内部有没有标点:粘连条目的典型症状是**内部零标点**(ASR 整段只在末尾补一个句号),而一个正常的长句内部一定有逗号。`stats` 把这两者分开报——前者进 `split: NEEDED`,后者进 `NOTE ... a single, already-punctuated sentence`,**后者原样留着交给第 6 步的 `resplit` 折行**。拉丁字母原文里这一类特别多,因为阈值(行宽的 3 倍)是按 CJK 的显示宽度定的,而一句英语 150~200 字符稀松平常;实测一份 89 条的英语字幕里有 17 条落在这一类,把它们当粘连去硬插句号,等于把 17 个完整句子腰斩。

`punctuation inside: N/M (X%)` 是旁证:比例高(≥50%)说明这个 ASR 老老实实保留标点,那么零标点的条目多半只是短到不需要逗号的单句,不是被吃了句读,`split: NEEDED` 里那批也要先读一眼再动手;比例极低说明 ASR 在成片地丢标点,补句读才是对的。

## 第 2 步:多个说话人不等于问得到真名

广播、对谈节目里每个说话人都有名字,纪录片/科普片却常常是"作者旁白 + 一堆匿名素材":新闻主播、街访记者、被采访的路人、政论节目发言人。实测一部 9 分钟的英语科普短片有 7 个 diarization 标签,除作者本人外 6 个全无姓名可查。问用户"各说话人分别是谁"在这里问不出东西,**要连处置方式一起给成选项**:

- **全部 `--drop`** —— 纪录片首选。画面切到谁在说一目了然,前缀纯属噪音;
- **换成角色名**(`新闻播报: ` `记者: ` `路人: `)—— 只在光靠画面分不清、或同一场景内多人交替时才值得;
- **只给非旁白加角色名**,旁白 `--drop` —— 折中。

别自作主张替用户选,但也别拿一个答不上来的问题去堵他。

全部 `--drop` 时,**去之前先把「标签 → 身份 → 条目号区间」的对照表写进 `_context/brief.md`**。前缀一去,谁在说这件事就只剩条目号能表达了,而翻译与复核子代理都要靠它切换语体:新闻播报是书面语、街访是口语、旁白是叙述腔。不留表,子代理只能从上下文猜,猜错了整段语体就崩。

## 第 2 步:原文可能不止一种语言,而 ASR 不会告诉你

纪录片/科普片插播新闻画面、街头采访、外国受访者原声时,ASR 会直接按那门外语听录下来,和主体语言混在同一份 SRT 里,没有任何标记——只有通读才发现。实测一部 9 分钟的英语短片里夹了 5 段荷兰语共 37 条(新闻播报、船屋居民抱怨、记者当街对质、被采访的路人、政论节目发言),其中记者与路人还是一来一往的对话。**别假定插播只有一两段、也别假定每段只有一个人说**。

处理:在简报里**逐条列出这些条目的原文与中文语义**,并说明各自的语体(新闻播报是书面语,街访是口语)。翻译子代理不一定懂那门外语,给了语义它才译得对;不给,它要么瞎猜,要么原样抄过去。外语段里的听录错误也在这里一并指出(它们比主体语言错得更多,ASR 在语言切换处最不可靠)。

一份字幕仍然只填**一个**原文语言给 `-l`(填主体语言)。`-l` 只影响标点风格与行宽,同属拉丁字母的语言之间没有差别;真正需要区分的是语义,而那由简报承担。

## 第 2 步:调研文件不带 URL 就沉淀不了来源

akiho-30 的两份调研文件写得很详细,但一个 URL 都没记。结果知识库的 `sources.md` 里没有一条节目相关来源,下次翻同一节目还得从 search 开始。所以调研角色的输出格式把「来源 URL」定为每条必填,查不到就写「search: <关键词>」,别留空。

## 第 3 步:merge 的判据与误合

`merge` 的判据是启发式的:上一条未以句末标点收尾 + 说话人前缀相同 + 间隔 ≤ 2 秒 + 合并后 ≤ 20 秒,才并入上一条;整条只有音频事件(如 `[オープニングミュージック]`)的条目不参与合并。脚本会打印合并后最长的 5 条条目号——**必须去看这几条**,它们最可能是误合。

前缀必须在 `merge` **之后**处理:`merge` 靠前缀相同与否判断能不能并条,先 `--drop` 会让它跨说话人乱合。

## 第 3 步:别名预替换的误伤面

日语子串匹配没有词边界。`鈴本` 作为 `涼本` 的错听是对的,但一份字幕里若真出现了姓鈴本的人,`auto` 替换就把他改没了;`和樹` 作为 `一樹` 的错听更危险,任何叫和樹的人都会中枪。所以别名表的 `mode` 缺省是 `ask`(只报位置),`auto` 要满足 `sediment_rules.md` 的三条硬判据。`replace` 的替换日志随 `_fix.srt` 一起看,复核子代理拿 `_fix.srt` 与原始副本对照时也要留意这些条目。

另外姓氏与全名要分两行:`鈴本さん` 出现 8 次、`鈴本あきほ` 只有 3 次,若只登记全名,姓氏单独出现的那 8 处永远替不到;若把 `鈴本さん` 登记成 `涼本あきほ` 的别名,替换会把「さん」吞掉。

## 第 4 步:时间轴不经过子代理

让 LLM 逐字抄几百组 `00:04:59,097 --> 00:05:02,595`,既占掉输出 token 的大半(时间戳是 token 密集的数字串,实测占六成上下),每一个数字又都是一次独立的出错机会——实测就出现过把 `00:04:59,097` 抄成 `00:05:00,100` 的漏网条目。改成只写译文后,时间轴不可能错,输出量也降三分之一以上,长字幕更不容易撞输出上限。

代价是漏行/多行会整体错位,所以格式里必须带编号,`apply` 会把编号完整性当硬约束校验(缺号、重号、越界、空译文一律报错并指名条目号,且**不写出任何文件**)。

## 第 4 步:分块翻译的硬要求

只有当 `_fix.srt` 条目数明显超出单子代理的一次处理上限(参考阈值 ≈ 1200 条)时才分块。第 3 步的整平会同时影响条目数:`merge` 通常把它降到原来的 2/3 左右(实测 783 → 570),`split` 则往回涨一些。

- 按 ~500~800 条一块切分,块要尽量大,不要切成 100 条的小块——块越大,拆分次数越少、上下文断点越少。
- 切分尽量沿自然段落边界(场景切换、长停顿、说话人轮换),不要机械按行号平切。
- 块首附上前一块**末尾 8~10 条**的原文与译文作衔接上下文,并在 prompt 里明确告知:本块是续译,必须沿用前块已确立的人称、语气、术语译名与行文风格。
- 各块子代理同样先读规范、简报、术语表、style,同样只输出 `编号<TAB>译文`。
- 各块写各自的 `<stem>_<lang>.part1.txt`、`.part2.txt`…,主代理按编号顺序 `cat` 成一份(编号是全局的,不要每块从 1 重新开始)。拼错了 `apply` 会当场报缺号/重号。

## 第 4 步:译文要有逗号,数字不要千位分隔符

第 6 步 `resplit` 的切点优先级是「空格 > 词边界近似 > 兜底硬切」,而 `clean` 正是把句中逗号转成空格、给 `resplit` 留下天然读点的。中文译文尤其吃这一条:`resplit` 估计词边界靠的是假名/汉字交替,**中文全是汉字,所有切点代价相同,没有标点就只能按行宽硬切**,实测会把「荷兰最深厚的国家传统」切成「…的国」/「家传统」。门槛:**一条译文超过约 18 个汉字就在语义停顿处加逗号**。

数字不写千位分隔符(写 `1000`,不写 `1,000`):目标语言是 CJK 时 `clean` 会把句中逗号转空格;夹在两个数字之间的逗号虽然已被保护,但混排里(如 `1, 000`、全角逗号)仍易出岔。

## 第 5 步:别指望复核子代理能替你把关,也别省模型

实测派出去的复核代理只改了 prompt 里明确点名的那一处,其余条目一字未动就回报"逐条核对完成"。复核清单为空或只有你点名的那几条时,**主代理必须自己读一遍译文**——尤其是术语表里的词、引述段落的人称、以及原文里拟声拟态词密集的条目(`ビリビリ` 被译成"又酸又辣"这种,只有对着原文看才抓得到)。

上面那次敷衍的复核用的是快模型;换成与主代理同档的模型跑同一份稿子,110 条里主动改了 37 条,抓出的错译包括 `Zoom out` 被译成"放大来看"(方向反了)、`too hard to ignore` 译成"难以抗拒"、荷兰语 `dek`(甲板)译成"船顶",还自查出「毫无防备的使用者」这类漏掉的修饰语——都不在 prompt 点名范围内。翻译子代理可以用快模型(它有简报和术语表兜着),**复核子代理不行**:它的活儿是发现别人没说的问题,而这恰恰最吃模型能力。主代理自己再读一遍的规矩照旧,两者是叠加关系。

复核是在 SRT 上定点 Edit,时间轴仍有被误改的可能(改一条正文时顺手动了上一行)。`check` 报 `DIFF timeline mismatch` 时不必派子代理回去改——时间轴逐条相等是硬约束,错位只可能是抄错,直接 `check --fix-timeline` 覆盖。条目数不一致时它会拒绝修(那说明问题不在时间轴,得先查清楚)。

## 第 6 步:切点质量取决于译文里有没有标点

「词边界近似」对日语是靠假名/汉字/片假名的交替估出来的;中文一整句全是汉字,没有这种交替可依,脚本另有一套高频虚词的启发式(在「的地得了」之后、「是在把被和但」之前优先断开,`-l zh` 时自动启用),但它只是近似。真正可靠的切点是**标点转成的空格**。抽查终稿时**专门看有没有被切开的词**——这是本步最容易出、也最影响观感的问题。发现了就回第 5 步给那几条译文补逗号,再重跑 `resplit`。

**译文保留了拉丁专名时要多看几眼。** 中文里写 `plaskrul 的支脚`、`某些 Urilift 小便池`,拉丁词两侧要加排版空格,而这种空格和 `clean` 由逗号转出来的真读点在文本里长得一模一样。脚本已按「专名与其黏着的中文成分不分家」把它降权(见 `_cut_cost` 的 `MIXED_SPACE_COST`),连续拉丁词内部的空格也不再当读点(`Shima Bulgariya` 不会被劈成两半),但靠的是字表启发式,覆盖不到「动词 + 专名宾语」这类要句法才判得出的搭配。残留的几处照老办法治:回第 5 步改那条译文——调整语序让专名挪到句首/句尾,或在真正的语义停顿处补一个逗号。实测一份 110 条的中文译文里这类坏切点有十来处,脚本降权后剩 2 处,改两条译文就清零了。给高频拉丁专名一个中文昵称(见 `translation-style.md` 手法 6)能从源头消掉这类切点。

## 第 6 步:插值的时间点没有音频依据

`resplit` 按译文各段的字宽比例在原条目区间内插值,而跨语言字数比不恒定(片假名外来语译成中文常压掉一半),长条目上误差能到秒级。第 3 步的 `split` 同样在插值,只是依据强一些(原文字符数≈音节数≈时长,同语言内相对可靠)。所以 `_<lang>_split.srt` 不是理所当然的终稿,要拿 `provenance` 的数字去问用户要哪一份。真正的解法是换一个能出词级时间戳的 ASR(WhisperX / faster-whisper `--word_timestamps` / ElevenLabs)重新转录;多数只落句级时间戳的 ASR(如 mossland-asr 的 `transcribe.py`)给不了这个。

## 第 8 步:错误进库会自我强化

知识库里的条目下次会被当成「已知」直接用,不再核查。所以沉淀角色只写提案、不碰库;`apply` 遇到译法不一致不覆盖只报冲突;`review_mode` 缺省 `full`,每次都看 diff。哪怕只是一个「自拟」译名,进库时 `notes` 也要写明「自拟」,下次遇到才知道它没有出处。
