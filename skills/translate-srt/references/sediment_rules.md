# 沉淀规则

给沉淀角色读。任务:把一次翻译(或一份 backfill 素材)里**下次还会用到**的东西,整理成 `_context/sediment_proposal.json`(格式见 [`kb_format.md`](kb_format.md))。不直接改知识库——合并、查重、判冲突由 `kb_tools.py apply` 做,落库与否由用户看过摘要后决定。

错误一旦进库会被当成「已知」永久复用,所以宁缺毋滥。

## 输入

- 本次 `_context/glossary.md`(含「来自知识库」与「本次新增」两节)
- `_context/brief.md`
- `_context/research/*.md`
- `_context/review_notes.md`(复核子代理的修改清单,有的话)
- `_context/hits.json`(哪些条目本来就在库里)
- 知识库现状:`index.md`、`aliases.tsv`、对应领域包的四个文件

## 沉淀什么

| 材料 | 去处 | 条件 |
| --- | --- | --- |
| 本次 glossary 里**实际在字幕中出现过**的新专名 | `aliases` + `entities` | 有可靠来源(官方页、wiki、多方一致);「自拟」译名也可以进,但 `notes` 要写「自拟」 |
| 主持人、常驻嘉宾、节目名、固定环节名 | `entities`(person / show)+ `aliases` | 反复出现的核心实体优先 |
| ASR 错听(3b 修正过、或 brief「疑似听录错误」里确认过的) | `aliases.asr_variants`,`mode: ask` | 错听写法必须是**字幕里真实出现过**的,不要自己造 |
| 行业用语、节目环节名、粉丝圈说法 | `glossary` | 与具体某一期无关、换一期还会出现的 |
| 调研时真正查到东西的 URL | `sources` | 官方 profile、节目官网、wiki 条目;搜索结果页不要 |
| 复核修改里体现出**偏好或惯例**的 | `style` | 用户明确说过的,或在 ≥2 个项目里重复出现的处理方式 |

## 不沉淀什么

- research 里未被采用的推测、「疑为」「可能是」的内容
- 只在本期出现、下次不会再见的东西:单集嘉宾提到的商品、某天的活动日程、听众来信的具体内容
- **听众投稿昵称(ラジオネーム)**:除非是节目常客(在 brief 或 research 里被标为常连),否则不进库。进库的用 `type: nickname`,`mode: ask`
- 复核里纯粹的错字、漏译这类一次性修正
- volatile 信息如果本次没用上
- 翻译子代理临场自拟的中文昵称(如把某个拉丁专名叫成「螺旋」)——那是单片内的约定,不是领域惯例

## 稳定性怎么标

- 译名、作品名、角色名、节目环节名、公司名 → `stable`
- 当前所属事务所、组合成员、在售商品、活动日程、比赛成绩、「最近」「今年」的事 → `volatile(YYYY-MM)`,月份写视频播出的月份
- 拿不准 → `volatile`。标 stable 的代价是错了也不会被重查

## 冲突怎么处理

- 新译法与库中现有译法不同 → **不要改提案去迁就库**,照本次采用的写法提交,`apply` 会标 CONFLICT 列出两个版本,由用户裁决。你在提案的 `notes` 里说明本次为什么这么译
- 同一实体新增信息 → 写在 `summary`,`apply` 会追加成「补充」行,不会重写已有内容
- 同一个错听写法可能对应两个人(`鈴本` 既可能是涼本也可能是真的鈴本某某)→ 不进 asr_variants,写在 entity 的 `summary` 里提醒

## `mode` 的判据

新条目一律 `ask`。只有满足全部三条才写 `auto`:

1. variant 长度 ≥ 3 个字,且不是常用词、不是别人名字的一部分
2. 这个错听在本次字幕里出现 ≥ 3 次,替换后主代理复核无一误伤
3. 这个 canonical 已经在库里(即这是第二次遇到)

## backfill 素材的特殊处理

`kb_tools.py backfill` 汇总的历史项目素材没有 hits.json,也可能没有 review_notes。按上面的规则挑,但更保守:历史 glossary 里「自拟」占比很高,只挑核心实体(主持人、常驻嘉宾、节目、固定环节、事务所、代表作角色)和有明确出处的术语。一次 backfill 的提案通常几十条,用户要逐条看,别把 200 条一次性倒进去。

## 产出

写 `_context/sediment_proposal.json`,然后回报:提案里各类各几条、你拿不准的条目(列出来让用户看)、以及你**没有**沉淀但值得一提的东西(比如库里某条译名和本次实际用法不一致)。不要自己跑 `apply`。
