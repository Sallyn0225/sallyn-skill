把一个由语音转文字生成的、不规范的外文 SRT,加工成规范的目标语言 SRT。文本层面的所有硬规则在 [`references/subtitle-rules.md`](references/subtitle-rules.md)(下称**规范**);派发的每个子代理都必须先 Read 规范。脚本路径以本 skill 目录为基准。

> **给子代理写路径时一律用正斜杠。** Windows 反斜杠路径在 prompt 里会被当成转义吃掉——`...\_context\research\01.md` 里的 `\_` 会变成 `_`,子代理于是在工作区**旁边**建了个 `<stem>_context/` 目录写进去,而且它自己毫不知情、照样回报"已写入"。写成 `E:/.../<stem>/_context/research/01.md` 就没这个问题。派发后顺手 `ls` 一下目标目录确认文件真的落在那里。

## 目录约定

为每部字幕建一个独立工作区,所有产出都在工作区内,外部原始字幕保持不动。以翻译 `how-to-code.srt` 为例:

```
<原 srt 同目录>/
  how-to-code.srt                  ← 原始字幕,保持不动
  how-to-code/                     ← 工作区(以原 srt 词干命名)
    how-to-code.srt                ← 原始副本(由脚本复制进来)
    how-to-code_merged.srt         ← merge 产物(输入已是一句一条时无此文件)
    how-to-code_fix.srt            ← 转录修正(原语言,整句一条)
    how-to-code_zh.txt             ← 翻译子代理的原始输出(只有「编号<TAB>译文」,不含时间轴)
    how-to-code_zh.srt             ← 翻译初稿(由 apply 把上面这份贴回时间轴生成)
    how-to-code_zh_fix.srt         ← 复核稿
    how-to-code_zh_split.srt       ← 重切分终稿 ★交付给用户的是这一份
    AGENTS.md                      ← 工作区说明(脚本生成)
    _context/                      ← 背景资料区
      brief.md                     ← 背景简报(占位 → 第 2 步填实)
      glossary.md                  ← 术语表(占位 → 第 2 步填实)
      research/                    ← 调研子代理的原始调研文件
        01-voice-actors.md
        ...
```

语言后缀用 ISO 639-1(zh、ja、en…)。下文 `<stem>` 指原 srt 词干(如 `how-to-code`),`<lang>` 指目标语言代码。

## 贯穿全流程:一条一整句

**修正与翻译全程都在"一条一整句"的形态上进行。**半句半句地翻,人称、语序、语气都接不上;十几句挤成一条地翻,时间轴又无从对齐。ASR 的失形有两种,方向相反,都要在翻译前整平:

| 失形 | 成因 | 症状 | 治法 |
| --- | --- | --- | --- |
| **切碎**:一句摊成三四条 | 按显示行宽切(`本日の` / `わびさびワード。`) | 多数条目**不以**句末标点结尾 | 第 3a 步 `merge` |
| **粘连**:十几句挤成一条 | 按静音切(VAD),说话人不停顿时整段打包、只在末尾补一个句号 | 条目**都以**句末标点结尾,但又长又挤(实测过单条 35 秒 / 462 显示列 / 内部零标点) | 第 3b 步补句读 + 3c 步 `split` |

同一份字幕可能两种都有。第 0 步用 `stats` 判定,第 3 步整平,第 4、5 步在整句形态上翻译与复核(中间产物条目少而长,**这是正常的**),第 6 步再用 `resplit` 按目标语言行宽切回观看用分条,交付这一份。

**还有第三种"又长又挤",它不是失形,不要治。** 一个条目超出宽度阈值,可能只是因为它本来就是一个长句。判据是内部有没有标点:粘连条目的典型症状是**内部零标点**(ASR 整段只在末尾补一个句号),而一个正常的长句内部一定有逗号。`stats` 把这两者分开报——前者进 `split: NEEDED`,后者进 `NOTE ... a single, already-punctuated sentence`,**后者原样留着交给第 6 步的 `resplit` 折行**。拉丁字母原文里这一类特别多,因为阈值(行宽的 3 倍)是按 CJK 的显示宽度定的,而一句英语 150~200 字符稀松平常;实测一份 89 条的英语字幕里有 17 条落在这一类,把它们当粘连去硬插句号,等于把 17 个完整句子腰斩。

**粘连必须在原文层(第 3 步)拆开,不能留给第 6 步的 `resplit`。** `resplit` 分配时间轴的依据是**译文**的字宽比例,而语言间的字数比并不恒定(片假名外来语译成中文常压掉一半以上),一条 35 秒的粘连条目按译文字宽均分,音画会漂移数秒。原文的字符数≈音节数≈时长,在原文层按句拆分可靠得多。

## 第 0 步:输入体检

```
python <skill目录>/scripts/srt_tools.py stats <原 srt 路径> -l <原文语言>
```

`stats` 不写文件,只打印条目形态(时长/宽度分布、最长的几条、以句末标点结尾的比例)并给出 `VERDICT`。**照它的判定走**——肉眼翻原 srt 判断不出粘连:粘连条目每条都以句号收尾,看起来完全正常,问题全藏在时长分布的尾部。

- `merge: NEEDED` —— 大量条目不收句,被行宽切碎了,第 3a 步跑 `merge`。
- `split: NEEDED` —— 有超长条目**且看起来是多句粘连**(缺省阈值:行宽的 3 倍或 12 秒),第 3 步要拆。它分两批:`have sentence punctuation inside` 的那批 `split` 直接就能切;`no punctuation inside at all` 的那批是内部一个标点都没有、脚本切不动,由你在 3b 手工补句读。
- `NOTE ... a single, already-punctuated sentence` —— **超长但不是粘连**:内部已有逗号等标点,说明 ASR 的标点是好的,它就是一个长句。**原样留着,什么都不要做**,第 6 步 `resplit` 会按行宽折行。绝不能为了让它变短而硬插句号——那是把一句话切成两个残句,翻译质量当场下降。拉丁语系原文里这一类很多:一句英语 150~200 字符再正常不过,而阈值是按 CJK 的显示行宽定的。
- 两个都 `not needed`、且没有 NOTE —— 输入已是一句一条,3a/3c 都跳过。
- `punctuation inside: N/M (X%)` —— 全篇有多少条目内部带标点。**这是判断上面那两批该怎么处置的旁证**:比例高(≥50%)说明这个 ASR 老老实实保留标点,那么零标点的条目多半只是短到不需要逗号的单句,不是被吃了句读,`split: NEEDED` 里那批也要先读一眼再动手;比例极低说明 ASR 在成片地丢标点,补句读才是对的。
- `speakers:` —— 列出条目里的说话人前缀及各自条目数。**两种前缀形态都认**:`関根瞳: 正文`(冒号式)和 `[S01] 正文`(方括号式,diarization 的占位标签,如 mossland-asr 的 `transcribe.py --diarize`)。只有一个说话人就该在 3b 去掉前缀,多个则在 3b 换成真名,见该步。没有这一行说明输入不带前缀,与说话人有关的动作全部跳过。

若能拿到上游 ASR 的转录 JSON(带 word 级时间戳),优先让用户用上游脚本本地重渲染出"一句一条"的 SRT 作为输入,**不产生二次计费**,质量也比启发式整平可靠(有真实词边界和更细的时间戳)。例如 ElevenLabs:

```
uv run python <asr仓库>/scripts/render_from_json.py <out.json> -f srt -o <name>_oneline \
    --max-line-width 999 --max-lines 1
```

但这条路常常走不通:多数 ASR 脚本只落 SRT 不存 JSON(如 DashScope Fun-ASR 的 `transcribe_to_srt.py`),转录 URL 也会过期;而且只有句级时间戳的 JSON 重渲染**解决不了粘连**——它的 sentence 边界就是 SRT 的条目边界,重渲染出来还是那几条(mossland-asr 的 `.json` 就是这样:`segments` 只有 `start`/`end`/`text`/`speaker`,与 SRT 一一对应,拿它重渲染毫无收益)。拿不到、或重渲染后 `stats` 仍报 `split: NEEDED`,就直接进第 1 步,由第 3 步整平。两条路径在第 3 步汇合,后续完全一致。

## 第 1 步:建立工作目录

在原 srt 同目录建工作区。运行:

```
python <skill目录>/scripts/srt_tools.py init <原 srt 路径>
```

脚本会:以 `<stem>` 在原 srt 同目录建 `<stem>/`(已存在则报错退出,re-run 由你自行判断);把原 srt 复制进去;生成 `AGENTS.md`、`_context/`(含占位的 `brief.md`、`glossary.md` 和空的 `research/`)。

完成标准:脚本打印 OK,工作区内有原始副本、`AGENTS.md`、`_context/brief.md`、`_context/glossary.md`、`_context/research/`。

## 第 2 步:提问、通读、调研

**2a 向用户提问。** 用 AskUserQuestion 问清三件事:原始语言(可提供"自动检测"选项;先扫一眼原 srt,**发现夹了外语插播段就在选项里写明**,别让用户以为只有一种语言)、目标语言、字幕的主题与热词(人名、作品名、专有名词;用户可留空或明说"跳过搜索")。

若 `stats` 报了说话人前缀(`名字: 正文` 或 `[S01] 正文`),**再多问一项:各说话人分别是谁**。ASR 未命名时前缀是 `speaker_0` / `[S01]` 这类占位符,必须拿到真名才能进术语表、才能译;已经是真名的则确认译名写法即可。

**只有一个说话人时不必问名字**(个人广播、单人 vlog 常见),但要告知用户前缀会在 3b 去掉——独角戏里每条都挂着名字只是噪音,还白占译文行宽。用户明确要保留的除外。

> **多个说话人不等于问得到真名。** 广播、对谈节目里每个说话人都有名字,纪录片/科普片却常常是"作者旁白 + 一堆匿名素材":新闻主播、街访记者、被采访的路人、政论节目发言人。实测一部 9 分钟的英语科普短片有 7 个 diarization 标签,除作者本人外 6 个全无姓名可查。问用户"各说话人分别是谁"在这里问不出东西,**要连处置方式一起给成选项**:
>
> - **全部 `--drop`** —— 纪录片首选。画面切到谁在说一目了然,前缀纯属噪音;
> - **换成角色名**(`新闻播报: ` `记者: ` `路人: `)—— 只在光靠画面分不清、或同一场景内多人交替时才值得;
> - **只给非旁白加角色名**,旁白 `--drop` —— 折中。
>
> 别自作主张替用户选,但也别拿一个答不上来的问题去堵他。

完成标准:原始语言与目标语言均已确定;主题要么拿到,要么用户明确跳过;有多个说话人前缀时,每个 speaker 都有对应的名字。

**2b 通读字幕,建立简报。** Read 工作区内的原始副本(过长则分段读完)。提炼:

- 内容概述;
- 出现的全部专名——人名/作品名/组织名,**含说话人前缀里的名字**,也含商品名、店名、菜单与等级名、活动名、听众投稿昵称(范围见规范"翻译"节);
- 疑似听录错误的词;
- 引述段落的位置(朗读来信、复述他人发言的起止)。写进简报,翻译子代理靠它切换人称与语体。
- **外语插播段的位置与逐条语义**(见下)。

> **原文可能不止一种语言,而 ASR 不会告诉你。** 纪录片/科普片插播新闻画面、街头采访、外国受访者原声时,ASR 会直接按那门外语听录下来,和主体语言混在同一份 SRT 里,没有任何标记——只有通读才发现。实测一部 9 分钟的英语短片里夹了 5 段荷兰语共 37 条(新闻播报、船屋居民抱怨、记者当街对质、被采访的路人、政论节目发言),其中记者与路人还是一来一往的对话。**别假定插播只有一两段、也别假定每段只有一个人说**。
>
> 处理:在简报里**逐条列出这些条目的原文与中文语义**,并说明各自的语体(新闻播报是书面语,街访是口语)。翻译子代理不一定懂那门外语,给了语义它才译得对;不给,它要么瞎猜,要么原样抄过去。外语段里的听录错误也在这里一并指出(它们比主体语言错得更多,ASR 在语言切换处最不可靠)。
>
> 一份字幕仍然只填**一个**原文语言给 `-l`(填主体语言)。`-l` 只影响标点风格与行宽,同属拉丁字母的语言之间没有差别;真正需要区分的是语义,而那由简报承担。

**2c 调研(用户跳过搜索则本步省略)。** 以用户给的主题为起点、结合字幕中读到的专名适当发散(例:声优名 → 其所属企划、参演作品、相关成员),并行派发 1~3 个联网搜索子代理,每个负责一个角度。**派发时由主代理指定每个子代理的编号与英文主题**(kebab-case,如 `01-voice-actors`),子代理不再以消息回报,而是把结果写入工作区内的 `_context/research/<编号>-<主题>.md`。每个调研文件固定两节:

- `## 事实要点` —— 与本字幕相关的事实要点;
- `## 术语表条目` —— 原语言写法 → 目标语言标准译名,查不到标"自拟"。

搜索结果若暴露出新的关键实体,可再派发一轮,新轮次按下一个编号继续落盘(总数仍按需控制,不刻意追求覆盖全部发散)。

**2d 汇总落盘。** 主代理 Read `_context/research/` 下全部调研文件,**不**合并成单一调研文件(避免信息漂移),而是据此编辑(替换占位内容)工作区内的 `_context/brief.md`(背景简报)和 `_context/glossary.md`(术语表)。术语表须覆盖字幕中出现的每个专名(查不到标"自拟")。

跳过搜索时,`_context/brief.md` 即主代理自己的通读总结,`_context/glossary.md` 由主代理拟定,同样写入这两个文件。

完成标准:`_context/research/` 下有若干调研文件(跳过搜索时为空);`_context/brief.md`、`_context/glossary.md` 已被填实;术语表覆盖字幕中每个专名,**说话人名也在其中**。

## 第 3 步:整平成一条一整句 + 修正转录错误 → `_fix.srt`

**3a 合并被切碎的条目(`stats` 报 `merge: NEEDED` 才做)。**

```
python <skill目录>/scripts/srt_tools.py merge <stem>/<stem>.srt -o <stem>/<stem>_merged.srt
```

`merge` 的判据是启发式的:上一条未以句末标点收尾 + 说话人前缀相同 + 间隔 ≤ 2 秒 + 合并后 ≤ 20 秒,才并入上一条;整条只有音频事件(如 `[オープニングミュージック]`)的条目不参与合并。脚本会打印 `merged: 783 -> 570 entries` 和合并后最长的 5 条条目号——**必须去看这几条**,它们最可能是误合。

**3b 复制,落实说话人前缀,再定点修改。** 把上一步的产物(`_merged.srt`,或没合并时的原始副本)**复制**为 `<stem>/<stem>_fix.srt`。

`stats` 报了说话人前缀的话,先用脚本一次性落实(**不要用 Edit 逐条改**,这是上百次机械替换):

```
python <skill目录>/scripts/srt_tools.py speakers <stem>/<stem>_fix.srt --map S01=関根瞳 --map S02=丸岡和佳奈
python <skill目录>/scripts/srt_tools.py speakers <stem>/<stem>_fix.srt --drop
```

- **多个说话人** —— 用 `--map` 把 2a 问到的真名换进去(键写标签本身,`S01` 或 `[S01] ` 都认),前缀统一成 `名字: ` 形态;值填**原语言**的真名,译名留到第 4 步按术语表翻。未被 `--map` 命中的前缀会以 `WARN` 列出,补一轮即可。
- **只有一个说话人** —— 用 `--drop` 整体去掉前缀(用户明确要保留的话,改用 `--map` 换成真名)。
- **多个说话人但全是匿名素材**(2a 里用户选了整体 `--drop`)—— 同样 `--drop`,但**去之前先把「标签 → 身份 → 条目号区间」的对照表写进 `_context/brief.md`**。前缀一去,谁在说这件事就只剩条目号能表达了,而翻译与复核子代理都要靠它切换语体:新闻播报是书面语、街访是口语、旁白是叙述腔。不留表,子代理只能从上下文猜,猜错了整段语体就崩。

前缀必须在 3a 的 `merge` **之后**处理:`merge` 靠前缀相同与否判断能不能并条,先 `--drop` 会让它跨说话人乱合。

然后 Read `_fix.srt`、用 **Edit 做定点修改**——不要整份重写。多数条目原样保留,定点编辑把输出量从上千行压到几十处,也避免重写时引入新错误。

主代理亲自做(需要对照背景简报做同音/近音纠错,不外包)。对照 `_context/brief.md`、`_context/glossary.md`,按规范执行:纠正听录错误(优先怀疑与术语表读音相近的词)、修正 3a 的误合与漏合、把归属错位的句首/句尾词移到相邻条目、删除纯口语废句、精简句内重复口语词、`[]`→`()`。保持原语言,不翻译;说话人前缀保持原样(译名留到第 4 步)。

**给 `stats` 在 `split: NEEDED` 下点名为 `no punctuation inside at all` 的条目补上句读**(原语言的句末标点),这是 3c 能拆开它们的前提——ASR 常常整段只在末尾补一个句号,内部一个标点都没有,脚本无从下手。补句读也属于"修正转录错误":漏标点本来就是转录的一部分错误。时间轴不要动,3c 会重新分配。

> **补之前先把这几条读一遍。**只有确实是好几句黏在一起才补。`stats` 的 `punctuation inside` 比例高(≥50%)时尤其要当心:那说明这个 ASR 是保留标点的,零标点的条目多半只是一句短到不需要逗号的话,补句号等于把它腰斩。
>
> **`stats` 打成 `NOTE ... a single, already-punctuated sentence` 的那批不在此列——一个字都不要动。**它们内部已经有标点,是货真价实的长句,`resplit` 会在第 6 步折行。拉丁语系原文里这批常常有十几条,别被条数吓到。

> 若 3a 跑过 `merge`,条目号已经变了,先对 `_fix.srt` 重跑一次 `stats` 拿本文件里的条目号,再动手。

**3c 拆开粘连的条目(`stats` 报 `split: NEEDED` 才做)。**

```
python <skill目录>/scripts/srt_tools.py split <stem>/<stem>_fix.srt -l <原文语言>
```

原地写回。脚本按句末标点把超长条目拆成一句一条(短的多句条目不动,留在一起翻译上下文更完整),时间轴在原条目区间内按各句显示宽度比例分配。打印 `split: 9 long entries -> 41 entries`;仍然超限、且内部无句读可切的条目会以 `WARN` 列出**产物里的条目号**(拆分会把后面的条目顺推)。

脚本把切不动的超长条目分成两档报,处置不同:

- `WARN ... no punctuation inside at all` —— 内部一个标点都没有,ASR 多半把句读吃了。**逐条读一遍**再决定:确实是几句黏在一起 → 回 3b 补句读,再跑一次 `split`;只是一句短到不需要逗号的话 → 留着。
- `NOTE ... a single, already-punctuated sentence` —— 内部已有标点,是一个真正的长句。**一个字都不要动**,第 6 步 `resplit` 会按行宽切开。

两档都不是必须清零的指标。**不要为了消掉它们硬插句号**,那会切碎句子,反而害了翻译。

`split` 已经包含 `normalize` 的工作(重排序、重编号),跑了它就不必再跑 `normalize`。

**3d 收尾。** 没跑 `split` 的话运行:

```
python <skill目录>/scripts/srt_tools.py normalize <stem>/<stem>_fix.srt
```

完成标准:`split`(或 `normalize`)输出 OK;`stats` 重跑后 `merge`/`split` 均不再 `NEEDED`,或每一处残留都能说明原因(如"这条本来就是一个长句");`NOTE ... a single, already-punctuated sentence` 不算残留,它本来就该留着;`merge` 的合并统计已抽查(至少看过最长的那几条);说话人前缀已落实(全部换成真名,或全部去掉,不留 `[S01]` 这类占位标签);原 srt 每一条都已处理(修正、合并、拆分、删除四者之一,多数条目原样保留也算已处理)。

## 第 4 步:翻译 → `_<lang>.srt`

**默认派发一个翻译子代理处理整份 `_fix.srt`**,不要拆分。理由:字幕是对话与叙事的连续体,人称、指代、称呼、语气常常跨条目绵延;整份交给同一子代理,它持有的上下文最完整、术语与风格自然一致,且只加载一次规范/简报/术语表、缓存命中最高。分块是降级手段,不是常态。

**子代理不输出 SRT,只输出译文。** 让它写一个纯文本 `<stem>/<stem>_<lang>.txt`,一行一条,格式固定为 `编号<TAB>译文`:

```
1	今天的侘寂词
2	从大家投稿的侘寂词里选出想到的东西说出来
```

时间轴根本不经过子代理,由主代理用 `apply` 从 `_fix.srt` 搬过来。这不是省事,是**消除一整类错误**:让 LLM 逐字抄几百组 `00:04:59,097 --> 00:05:02,595`,既占掉输出 token 的大半(时间戳是 token 密集的数字串,实测占六成上下),每一个数字又都是一次独立的出错机会——实测就出现过把 `00:04:59,097` 抄成 `00:05:00,100` 的漏网条目。改成只写译文后,时间轴不可能错,输出量也降三分之一以上,长字幕更不容易撞输出上限。

代价是漏行/多行会整体错位,所以格式里必须带编号,`apply` 会把编号完整性当硬约束校验(缺号、重号、越界、空译文一律报错并指名条目号,且**不写出任何文件**)。

每个翻译子代理的 prompt 必须包含:`<stem>/<stem>_fix.srt` 路径与上面的输出路径和格式,并要求**先 Read 规范、`_context/brief.md`、`_context/glossary.md` 再动手**(不再把简报/术语表内联进 prompt),以及:按信达雅翻译为目标语言,与 `_fix.srt` 的条目**一一对应、编号照抄、不合并不拆条不增删**;**译文里不能出现换行和制表符**(一条一行,否则错位);**条目带 `名字: ` 前缀的,前缀要保留并按术语表译名翻译**。

还有两条是给下游脚本铺路的,必须写进 prompt:

- **每条译文内部要按语义停顿打逗号,别让一条长句一个标点都没有。** 第 6 步 `resplit` 的切点优先级是「空格 > 词边界近似 > 兜底硬切」,而 `clean` 正是把句中逗号转成空格、给 `resplit` 留下天然读点的。中文译文尤其吃这一条:`resplit` 估计词边界靠的是假名/汉字交替,**中文全是汉字,所有切点代价相同,没有标点就只能按行宽硬切**,实测会把「荷兰最深厚的国家传统」切成「…的国」/「家传统」。给一个可执行的门槛:**一条译文超过约 18 个汉字就在语义停顿处加逗号**。
- **数字不要写千位分隔符**(写 `1000`,不写 `1,000`)。目标语言是 CJK 时 `clean` 会把句中逗号转空格;夹在两个数字之间的逗号虽然已被保护,但混排里(如 `1, 000`、全角逗号)仍易出岔,源头上避开最省事。

**只有当 `_fix.srt` 条目数明显超出单子代理的一次处理上限(参考阈值 ≈ 1200 条;接近或超过才考虑)时**,才回退到分块翻译,以避免单次输出撑爆上下文/输出限额。注意第 3 步的整平会同时影响条目数:`merge` 通常把它降到原来的 2/3 左右(实测 783 → 570),`split` 则把粘连条目拆开、往回涨一些。以 `_fix.srt` 的实际条目数为准,这个阈值很少触发。回退时的硬要求:

- 按 ~500~800 条一块切分,块要尽量大,不要切成 100 条的小块——块越大,拆分次数越少、上下文断点越少越好。
- 切分尽量沿自然段落边界(场景切换、长停顿、说话人轮换),不要机械按行号平切。
- 块首附上前一块**末尾 8~10 条**的原文与译文作衔接上下文(比 2~3 条更厚),并在 prompt 里明确告知:本块是续译,必须沿用前块已确立的人称、语气、术语译名与行文风格,不得另起一套。
- 各块子代理同样先 Read 规范、`_context/brief.md`、`_context/glossary.md`,同样只输出 `编号<TAB>译文`。
- 各块写各自的 `<stem>_<lang>.part1.txt`、`.part2.txt`…,主代理按编号顺序 `cat` 成一份 `<stem>_<lang>.txt`(编号是全局的,不要每块从 1 重新开始)。拼错了 `apply` 会当场报缺号/重号。

最终(单代理或分块拼接后)运行:

```
python <skill目录>/scripts/srt_tools.py apply <stem>/<stem>_fix.srt <stem>/<stem>_<lang>.txt -o <stem>/<stem>_<lang>.srt -l <lang>
python <skill目录>/scripts/srt_tools.py check <stem>/<stem>_fix.srt <stem>/<stem>_<lang>.srt
```

`apply` 已经包含 `clean` 的工作(标点规范化),不必再跑一次 `clean`。它校验通过才写文件,报错时一个字节都不写——照它点名的条目号让子代理补齐或改正,再跑一次。

`check` 会报出条目数差异、时间轴错位的条目号,以及译文与原文逐字相同的条目号(`NOTE`,提示可能漏译——纯汉字专名、按术语表保留原文的节目名合法相同,需自行判断)。走 `apply` 这条路时间轴不会错,`check` 在这一步主要是查漏译。

完成标准:`apply` 输出 OK;`check` 打印 `OK: aligned`,或每一处 `DIFF`/`NOTE` 都能说明原因;分块时各块编号无重叠无遗漏。

## 第 5 步:复核 → `_<lang>_fix.srt`

派发一个审查子代理,给它:`<stem>/<stem>_fix.srt`(原文基准)、`<stem>/<stem>_<lang>.srt`(待审译文),并要求先 Read 规范、`_context/brief.md`、`_context/glossary.md`。

任务:**先把 `_<lang>.srt` 复制为 `_<lang>_fix.srt`,再对有问题的条目做 Edit**(理由同第 3b:多数条目无需改动,定点编辑省输出且不引入新错误)。逐条对照原文与译文,检出并直接修正漏译、错译、术语不一致、说话人前缀丢失或译名不一致、不符合规范的条目。改完跑:

```
python <skill目录>/scripts/srt_tools.py clean -l <lang> <stem>/<stem>_<lang>_fix.srt
python <skill目录>/scripts/srt_tools.py check <stem>/<stem>_<lang>.srt <stem>/<stem>_<lang>_fix.srt
```

然后回报修正清单(条目号+改动原因)。

复核是**在 SRT 上定点 Edit**,所以时间轴仍有被误改的可能(改一条正文时顺手动了上一行)。`check` 报 `DIFF timeline mismatch` 时不必派子代理回去改——时间轴逐条相等是硬约束,错位只可能是抄错,直接覆盖:

```
python <skill目录>/scripts/srt_tools.py check <stem>/<stem>_fix.srt <stem>/<stem>_<lang>_fix.srt --fix-timeline
```

条目数不一致时它会拒绝修(那说明问题不在时间轴,是条目对不上,得先查清楚)。

> **别指望复核子代理能替你把关。** 实测派出去的复核代理只改了 prompt 里明确点名的那一处,其余条目一字未动就回报"逐条核对完成"。复核清单为空或只有你点名的那几条时,**主代理必须自己读一遍译文**——尤其是术语表里的词、引述段落的人称、以及原文里拟声拟态词密集的条目(`ビリビリ` 被译成"又酸又辣"这种,只有对着原文看才抓得到)。
>
> **复核这一步别省模型。** 上面那次敷衍的复核用的是快模型;换成与主代理同档的模型跑同一份稿子,110 条里主动改了 37 条,抓出的错译包括 `Zoom out` 被译成"放大来看"(方向反了)、`too hard to ignore` 译成"难以抗拒"、荷兰语 `dek`(甲板)译成"船顶",还自查出「毫无防备的使用者」这类漏掉的修饰语——都不在 prompt 点名范围内。翻译子代理可以用快模型(它有简报和术语表兜着),**复核子代理不行**:它的活儿是发现别人没说的问题,而这恰恰最吃模型能力。主代理自己再读一遍的规矩照旧,但两者是叠加关系,不是替代。

> `-l <lang>`(ISO 639-1)决定 clean 的标点风格:zh/ja/ko 走 cjk 风格(句中非成对标点转空格、句尾不留句号);其余拉丁/西里尔等走 western 风格(保留 ASCII 标点与破折号族、句尾留句号)。western 假定译文标点已拉丁化,仅额外清理残留的 CJK 全角标点(如 `，、。；：～` 转空格),不做全角→半角全面规范化。缺省为 cjk。说话人前缀(`名字: `)在两种风格下都原样透传,不参与标点清理。

完成标准:子代理回报"逐条核对完成",附修正清单(可为空);`check` 无未解释的 `DIFF`。

## 第 6 步:重切分 → `_<lang>_split.srt`

到这一步译文还是"整句一条",单条可能长达十几秒。按目标语言行宽切回观看用分条:

```
python <skill目录>/scripts/srt_tools.py resplit -l <lang> <stem>/<stem>_<lang>_fix.srt -o <stem>/<stem>_<lang>_split.srt
```

切点按「空格(clean 留下的天然读点)> 词边界近似 > 兜底硬切」择优,并遵守换行禁则(闭括号/小书假名/长音符不可行首等);时间轴在原条目区间内按各段宽度比例分配,过短的段从相邻长段借时间。行宽缺省 cjk 38 列 / 其余 42 列(全角算 2 列),可用 `--max-line-width` 调整。

> **切点质量取决于译文里有没有标点。** 「词边界近似」对日语是靠假名/汉字/片假名的交替估出来的;中文一整句全是汉字,没有这种交替可依,脚本另有一套高频虚词的启发式(在「的地得了」之后、「是在把被和但」之前优先断开,`-l zh` 时自动启用),但它只是近似。真正可靠的切点是**标点转成的空格**,所以第 4 步要求译文按语义停顿打逗号——一条超过约 18 个汉字还一个标点都没有,就只能靠启发式碰运气。
>
> 抽查终稿时**专门看有没有被切开的词**——这是本步最容易出、也最影响观感的问题。发现了就回第 5 步给那几条译文补逗号,再重跑 `resplit`。
>
> **译文保留了拉丁专名时,这一步要多看几眼。** 中文里写 `plaskrul 的支脚`、`某些 Urilift 小便池`,拉丁词两侧要加排版空格,而这种空格和 `clean` 由逗号转出来的真读点在文本里长得一模一样。脚本已按「专名与其黏着的中文成分不分家」把它降权(见 `_cut_cost` 的 `MIXED_SPACE_COST`),连续拉丁词内部的空格也不再当读点(`Shima Bulgariya` 不会被劈成两半),但靠的是字表启发式,覆盖不到「动词 + 专名宾语」这类要句法才判得出的搭配。**残留的几处照老办法治:回第 5 步改那条译文**——调整语序让专名挪到句首/句尾,或在真正的语义停顿处补一个逗号,给切点一个比排版空格更便宜的去处。实测一份 110 条的中文译文里这类坏切点有十来处,脚本降权后剩 2 处,改两条译文就清零了。

注意这一步会改变条目数与时间轴,所以**不要**对它跑 `check`——`check` 只用于第 4、5 步那种应当逐条对齐的场合。

### 交付哪一份,由用户定,不由你定

**`resplit` 切出来的时间点是算出来的,没有音频依据。** 它按译文各段的字宽比例在原条目区间内插值,而跨语言字数比不恒定(片假名外来语译成中文常压掉一半),长条目上误差能到秒级。第 3 步的 `split` 同样在插值,只是依据强一些(原文字符数≈音节数≈时长,同语言内相对可靠)。

所以 `_<lang>_split.srt` **不是理所当然的终稿**。跑完 resplit 后,对每一份候选产物跑:

```
python <skill目录>/scripts/srt_tools.py provenance <原 srt 路径> <stem>/<stem>_<lang>_fix.srt
python <skill目录>/scripts/srt_tools.py provenance <原 srt 路径> <stem>/<stem>_<lang>_split.srt
```

它会打印每份产物有多少时间点来自原始 ASR、多少是插值的,并验证插值点是否都严格落在原条目区间内部(越界 = 真实边界被移动了,那是 bug,必须查)。**拿这两个数字去问用户要哪一份**,别替他决定:

- `_<lang>_split.srt` —— 观看体验最好(单条不超行宽),但插值点最多;
- `_<lang>_fix.srt` —— 只含第 3 步那批依据较强的插值点,代价是单条可能十几秒、一行显示不下;
- 要求零插值的话,只能回到原始 ASR 的条目边界(把译文合并回去),单条会更长;
- 真正的解法是**换一个能出词级时间戳的 ASR**(WhisperX / faster-whisper `--word_timestamps` / ElevenLabs)重新转录,拿真实词边界来切——见第 0 步。多数只落句级时间戳的 ASR(如 mossland-asr 的 `transcribe.py`,只有 `json`/`diarized_json`/`text`)给不了这个。

完成标准:resplit 输出 OK;`provenance` 无越界报错;抽查若干条,确认单条不超行宽、时间轴单调不重叠、说话人前缀完整、没有把词切在中间;**已把插值数字告知用户并拿到他对交付形式的选择**。

## 第 7 步:总结

主代理抽查终稿的开头、中间、结尾各若干条,确认整体质量,然后向用户报告:工作区路径、产出文件(`_fix`/`_<lang>`/`_<lang>_fix`/`_<lang>_split`)的路径并**指明用户选定的那一份是最终交付物**、`_context/` 内的背景资料(`brief.md`、`glossary.md` 及 `research/` 下调研文件)、修正要点(转录纠错了什么、复核改了什么),以及**时间轴里有多少个插值点**(第 6 步 `provenance` 的数字)。

插值这件事**必须主动说**,别等用户问起。他有权知道交付物里哪些时间点是音频量出来的、哪些是脚本算出来的。
