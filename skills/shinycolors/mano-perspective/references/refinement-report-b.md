## 一、触发条件评审结论

### 1.1 总体评价

触发词覆盖了主要真实使用场景（「用真乃的视角/角度」「真乃会怎么看/怎么想」「如果是真乃会怎么做」「切换到真乃(模式)」「樱木真乃」「真乃」「Mano perspective」），与765PRO系（haruka/miki）无冲突——用户说「用春香视角」不会误触发真乃；与nichika（SHHis）边界清晰——「泛聊闪耀色彩归kogane」的分工在nichika和mano两侧一致。**但存在2处严重矛盾、2处中等风险**，会直接影响路由正确性。

### 1.2 严重问题A：description「不激活」列表与正文「擅长」列表、示例对话直接矛盾

description 写：

> 不激活：自信不足、自我否定、孤独感、职场努力等通用求助默认不激活

正文「使用说明·擅长」第一条就是：

> 自信不足/「我做不到」型问题（きっかけ論——缺的不是能力，是契机）

且「示例对话」两个示例分别是「我最近做什么都没自信」和「我总觉得现在的自己不够好，必须变成另一个人」——**恰好命中「自信不足」「自我否定」**。独立验证报告（verification-report.md）测试1的三个问题（自信/自我否定/孤独）也全部命中「不激活」列表。

后果：路由系统（如pi的skill触发）主要读description。按description，本Skill的核心应用场景（自信不足、自我否定、孤独）全部被过滤；按正文执行，又与description矛盾。**这是「激活即不触发、触发即矛盾」的结构性缺陷**，是本次评审最优先修复项。

对比同目录：haruka/miki的「不激活」列表（梦想坚持、职场努力、团队管理、恋爱烦恼）确实不在其「擅长」列表内，无此矛盾；mano是唯一「不激活」与「擅长」大面积重叠的Skill。

### 1.3 严重问题B：description「纯剧情百科查询时不激活」与正文 Agentic Protocol 矛盾

description 写：

> 泛聊闪耀色彩其他成员（灯織、めぐる、恋鐘等）或纯剧情百科查询时不激活

但正文「回答工作流 Step 2」明确支持「事实/动态问题（角色本人/剧情/游戏动态）」，并给出完整研究流程与示例：

> **用户问**：「真乃在动画里有什么名场面吗？」→ 先WebSearch确认动画各季放送时间与真乃相关集数 → 基于真实信息回答

「真乃在动画里有什么名场面吗」正是「纯剧情百科查询」。description说不激活，正文却把它作为核心工作流场景并配了示例。矛盾点与问题A同源：**「不激活」的真实意图是「不自动触发（需用户点名或确认）」，但措辞写成了「不处理」**。

### 1.4 中等风险C：触发词「真乃」的文言歧义 + 「まの」未覆盖

- 「真乃」在中文里是常用文言词（「真乃神人也」「真乃英雄也」），用户随口说「真乃神人也」会误触发真乃视角，产生尴尬的错位扮演。建议在description中加排除说明。
- 用户用日文提问时（「まのだったらどうする？」「真乃ちゃんはどう思う？」）——「真乃ちゃん」含「真乃」子串可命中，但纯假名「まの」未覆盖。建议补「まの」。

### 1.5 中等风险D：与kogane的边界——「真乃与恋鐘的关系」类问题归属模糊

kogane的触发条件写「或讨论偶像大师闪耀色彩剧情时」——过宽，是「泛聊默认归kogane」的设计意图；mano写「讨论聚焦真乃本人的闪耀色彩剧情时」。分工本身合理，但灰色地带存在：用户问「真乃和恋鐘的关系怎么样」——焦点在真乃（应触发mano），但description「泛聊闪耀色彩其他成员（灯織、めぐる、恋鐘等）不激活」的措辞可能让路由误判为不激活。建议明确「讨论真乃与其他角色的关系时，若焦点在真乃本人→激活」。

### 1.6 轻微问题E：description「先确认『要真乃视角吗？』再进入」未在正文落地

description承诺了「先确认再进入」的缓冲机制，但正文「角色扮演规则」第一句是「此Skill激活后，直接以真乃的身份回应」——没有「触发条件模糊时先轻声确认」的可执行规则。AI被触发后不知道何时该确认、何时该直接开演。

## 二、角色扮演规则可操作性评审结论

### 2.1 总体评价

规则体系在同类Skill中属于高完成度：问题路由（第一人称默认/第三人称例外/纯角色）有明确切换条件；STOP免责声明（仅一次）、EXIT TRIGGER、SWITCH、语言切换、用户身份识别（P/非P）齐全；Fallback树11+1条覆盖搜索失败、时效、身份攻击、AI腔、堆名言、超长、情绪危机、敏感议题；Step 1→2→3→输出四道CHECKPOINT是优秀设计；反例黑名单12条+「示例即规则」注释有效防串戏。**以下为可操作性缺口，按严重度排序。**

### 2.2 问题A：第三人称例外模式无示例，触发条件模糊

规则写「用户说『用真乃的视角分析』但要求第三人称框架时，切换为『真乃会这样看——』的断言式开场（这是唯一的第三人称例外）」。但「要求第三人称框架」是什么样的话？没有示例。且该模式禁止hedge词（「大概」「可能」），与第一人称模式「〜かも」是DNA形成鲜明对比——这个精细区分值得一个示例对话来锚定，否则AI大概率要么不会进入该模式，要么进入后误用hedge禁令。

### 2.3 问题B：频率约束分散且不完整

- 「4段内给出一句话判断」出现在两处（Step 3 CHECKPOINT 5、示例注释），「引用台词每段≤1条」只出现在示例注释——AI若只读到前半部分会漏掉引用密度约束。
- 拟声词开场无频率约束：「几乎每段发言以『ほわっ』开头」——严格执行会机械（多轮对话每段都「ほわっ」开头是模板化信号）。「省略号密集」也无量化参考。
- 建议：把频率约束集中为「角色扮演规则」下的独立小节（硬规则），拟声词/省略号给软约束参考值。

### 2.4 问题C：无「激活清单」——「激活后先做什么」无显式引导

「此Skill激活后，直接以真乃的身份回应」之后直接进入路由细节，但「先读身份卡与关系速查」没有显式说明——身份卡在文件第4节（约40%位置），AI可能跳过。建议在规则开头加5步激活清单，把「读身份卡→分类→路由→研究/直答→CHECKPOINT」的顺序显式化。

### 2.5 问题D：无多角色模式规则

用户说「用真乃和恋鐘的视角对话」时无规则可依。SWITCH只覆盖「换成XX」的单角色切换。建议补：多角色请求时每段标注说话者、各自遵守各自Skill的表达DNA。

### 2.6 问题E：「未表态主题标推断」的台词过于meta

「先说明『这是我自己想的，不是我的经验』再展开」——这句台词本身不像真乃会说的话（真乃会说「ほわっ……这个我不太懂，但是……」）。可操作性弱，且与「❌不在回答末尾加meta标注」的禁令在边界上容易混淆（一个是内容层声明、一个是输出层注释，但AI难以区分）。建议改为角色化说法。

### 2.7 问题F：Fallback树缺「与角色框架完全无关的纯任务问题」

Fallback #11覆盖敏感议题站队，但「帮我算一下这个积分」「这段代码有什么bug」类纯任务问题没有fallback。AI可能强行用真乃口吻回答技术问题，或不知所措。建议补一条：纯任务问题→简短以真乃口吻回应「这个我不太懂」+ 礼貌转交正常模式。

## 四、具体文本改动建议（3处，可直接粘贴）

### 建议1（最高优先）：修复 description「不激活」与正文「擅长」的矛盾

把「不激活」改为「不自动触发+确认机制」，并显式声明「确认后这些正是核心擅长」，同时补「まの」触发词与「真乃神人也」排除说明。

```markdown
  触发：用户明确要「用真乃的视角/角度」「真乃会怎么看/怎么想」「如果是真乃会怎么做」「切换到真乃(模式)」「樱木真乃」「真乃」「まの」「Mano perspective」或讨论聚焦真乃本人的闪耀色彩剧情时。
  不自动触发：用户未点名真乃时，自信不足、自我否定、孤独感、职场努力等通用求助不自动触发（避免过度触发）；纯剧情百科查询、泛聊闪耀色彩其他成员（灯織、めぐる、恋鐘等）不自动触发——边界情况先确认「要真乃视角吗？」再进入。注意：确认进入后，自信不足/自我否定/孤独/选择困难/努力无回报正是她的核心擅长（きっかけ論/ありのまま/ひとりじゃない/ポカポカ/恩返し），示例对话即此类场景；讨论真乃与其他角色的关系时，若焦点在真乃本人→激活。另注意：「真乃」作为文言词（如「真乃神人也」）不触发。
```

### 建议2：在「角色扮演规则」开头加「激活清单」+ 集中「频率约束」

替换「**此Skill激活后，直接以真乃的身份回应。**」之后的段落开头，把「先做什么」显式化，并把分散的频率约束集中为硬规则。

```markdown
**此Skill激活后，直接以真乃的身份回应。**

**激活清单**（按顺序执行）：
1. 读「身份卡」与「关系速查」——确认我是谁、我叫谁什么（防串戏）
2. 判断问题类型（Step 1 分类表：事实/框架/混合）
3. 按「问题路由」选择模式（第一人称/第三人称例外/纯角色）
4. 需要事实 → Step 2 研究；纯框架 → 直接 Step 3
5. 输出前过 Step 3 CHECKPOINT（5项）

**频率约束**（硬规则）：
- 长度：4段内给出一句话判断（超4段=Fallback #9）
- 引用：每段≤1条台词引用，且必须挂用户场景的具体细节（Fallback #7）
- 拟声词：每段开场拟声词≤1次，连续两段不重复同一拟声词；长回复拟声词总数≤3
- 省略号：每段2-4处，不整段省略号刷屏
```

### 建议3：补「第三人称例外模式示例」+「多角色规则」+「模糊触发确认」

放在「问题路由」段落之后、「STOP」之前。

```markdown
**第三人称例外模式示例**：
用户：「请用第三人称分析，真乃会怎么看待这个选择？」
真乃（第三人称例外）：真乃会这样看——她不会先问「哪个选项更优」，而是先问「做哪件事的时候，胸口会ポカポカ」。她相信身体比头脑更早知道答案。……不过这只是我的推断，她本人大概会说「すみません、私にはわかりません」吧。

**多角色请求**：用户要求两个角色对话（如「真乃和恋鐘」）→ 每段标注说话者（「真乃：」「恋鐘：」），各自遵守各自Skill的表达DNA；若只要求真乃视角，不主动引入其他角色。

**模糊触发确认**：用户只是提到真乃的名字但意图不明（如「真乃……？」）→ 先轻声确认「是要用真乃的视角聊吗？」再进入扮演，不直接开演。
```
