# Phase 5 精炼评审 · Agent B（skill-creator 视角）

**对象**：`chiyoko-perspective/SKILL.md`
**评审视角**：skill-creator——关注「AI 拿到这个 skill 后能不能稳定、不困惑地执行」，找可操作性问题
**日期**：2026-08-25
**结论**：整体框架成熟（6 心智模型 + 8 启发式 + 双模式开关 + Agentic Protocol 均到位），但在**可操作性**层面有 3 处会让 AI 卡壳或下行的硬伤，均为「写了引用却没写定义」或「同类 skill 有约束表而本 skill 缺失」。下面分 3 方面给出发现 + 理由，并在最后给 3 处「原文→改后」的具体改动。

---

## 方面 1：激活触发条件是否覆盖真实使用场景

### 发现 1.1：触发叫法覆盖良好，但漏了最高频昵称「チョコ」（裸称）

description 触发名单列了「智代子/ちよこ/チョコちゃん/ちょこ先輩/chiyoko/園田智代子/园田智代子/Sonoda Chiyoko」，这覆盖了大部分叫法。但**漏了裸称「チョコ」**——而这是樹里对她的固定称呼（关系速查表里自己写了「樹里ちゃん（同级、じゅりちょこ）」「樹里…チョコ」），粉丝社区也大量用「チョコ」指代她。

skill 在「注意」段把「チョコ」当普通词（食物）处理、排除出触发列，这是**有意的消歧**（避免「聊现实巧克力」误触发），权衡合理。但代价是：用户说「チョコ会怎么看这个」时不会自动触发。对「真实使用场景」而言这是一个可见缺口——裸称比「ちよこ」更常用。

**建议**：不必把裸「チョコ」加进自动触发（消歧代价太大），但可在「注意」段补一句**条件触发**：上下文已指向闪耀色彩/放クライ/偶像话题时，裸「チョコ」也触发。这样既保留消歧，又不漏真实叫法。

### 发现 1.2：不自动触发的边界合理且与同类 skill 一致

「我太普通了/没有个性/我是不是只是别人的替身/被否定好不甘心/我是不是给朋友添麻烦了」不自动触发，先问「要听智代子的想法吗？」——这与 meguru/asahi 的设计范式一致（泛化求助不自动触发，避免误触），且确认后这些正是核心战场，逻辑自洽。✅ 无需改。

### 发现 1.3：转交规则完整，但存在一个**悬空引用**（kogane-perspective 不存在）

转交规则覆盖了：あすみ本人（暂无视角，明确告知）、其他放クライ成员本人（暂无视角）、其他组合成员本人（归对应 perspective）、纯百科考据（情报模式）。结构完整。

**但**：第 7 行写「泛聊放クライ或闪耀色彩整体（焦点不在她，**泛聊剧情归 kogane-perspective**）」——而本项目 `.agents/skills/` 下**并不存在 kogane-perspective**（仅有 asahi/chiyoko/fish-tts/hana/huashu-nuwa/meguru）。这是一个**悬空指针**：AI 被指示转交给一个不存在的 skill，会卡在「kogane-perspective 是什么？我该转去哪？」。

这是项目级共性问题（meguru/asahi 的 skill 也都引用了 kogane-perspective），但对单个 skill 的可操作性而言仍是 broken pointer。建议至少在 chiyoko 内做**防御性写法**，不要假设目标存在。

### 发现 1.4：与现有 3 个 perspective 的触发边界清晰无重叠

- めぐる（だよね系/イルミネ）、あさひ（っす系/Straylight）、羽那（CoMETIK）、智代子（です系/放クライ）——语尾基底不同、组合不同，**无重叠**。
- 转交交叉引用正确（めぐる→meguru、あさひ→asahi、羽那→hana）。
- 「注意」段对「チョコ」的消歧与 asahi 对「あさひ」的消歧范式对齐。✅

## 方面 2：角色扮演规则的可操作性

### 发现 2.1：问题路由——有，且比同类更细 ✅

「分析/评价/怎么看」→第一人称但可结构化；「扮演/角色对话」→纯角色模式；「用视角分析但要求第三人称框架」→「智代子会这样看——」断言式开场（唯一第三人称例外）。三档清晰可执行。✅

### 发现 2.2：频率约束——**严重缺失**（与 meguru/asahi 对照）

这是本 skill 最大的可操作性问题。meguru（line 417）和 asahi（line 417）都有一张** consolidated「### 频率约束（防滥用）」表**，含：每段限额、段落长度上限（meguru 单段≤120字、asahi≤150字）、回复长度上限、开头规则、**长对话校准（每 3 轮自检一次防漂移）**。

chiyoko 的频率规则**散落**在「对话节律」和「语气硬规则」里，只有：
- 「每 2-3 句插入一次チョコ語録或えへへ」
- 「每轮≤1次慌乱收场」

**缺失**：
1. 没有 consolidated 频率表（AI 需要翻多处拼凑）；
2. **没有段落长度上限**（meguru/asahi 都有，防冗长漂移的关键约束）；
3. **没有 えへへ 的每段上限**——143 条语料里 えへへ 仅 10 次（≈7%），但「每 2-3 句插一次」若全用 えへへ，会远超原作频率，导致 えへへ 滥用、人设滑向「傻笑少女」；
4. **没有「长对话校准」**——meguru/asahi 都有「每 3 轮自检一次频率/反例黑名单/有无滑向 AI 腔」，chiyoko 只有一次性 checkpoint，长对话易漂移。

### 发现 2.3：失败预防——大部分到位，但 hedge 禁止只列了少数词 ✅⚠️

- ✅ hedge 禁止（「大概/可能/如果是她」）
- ✅ 反例黑名单完整（だよ/だよね/だもん/じゃん/っす/あたし/あはは大笑/直呼P去さん/对チョコ否定）
- ⚠️ 但 hedge 词清单偏少，没有像 asahi 那样显式列「应该是…吧/我猜…/也许」等中文 hedge。中文输出时 AI 仍可能滑出 hedge。建议补中文 hedge 黑名单。

### 发现 2.4：双模式语气开关——可执行 ✅

P模式/あすみ模式表清晰，判定规则明确（「一旦对话对象是あすみ或用户说『我是あすみ』，敬语全部卸下」），且模型六给了崩塌机制（逞强→「ごめんなさい」）。可执行。✅

### 发现 2.5：引用了**不存在的 Fallback 编号**（#2/#7/#10）

这是最致命的可操作性问题。skill 在 3 处引用了 Fallback 编号：
- line 196：时效红线 →「走Fallback #2」
- line 146：引用台词每段≤1条 →「（防Fallback #7）」
- line 221：严重危机 →「走Fallback #10」

**但全 skill（含 references/）没有任何 Fallback 编号列表或定义。** AI 看到「严重危机走Fallback #10」会直接卡住：「Fallback #10 是什么？我该做什么？」——尤其在**严重危机**这个最不该卡的场景。

> 对照：meguru 在 line 179 有「豁免：Fallback #10（危机）与『认真/受伤模式』不强制元气」——至少在语境里半定义了 #10=危机；chiyoko 连这个都没有，是完全悬空。

这是项目级共性（meguru/asahi 同样无 Fallback 总表），但 chiyoko 必须自洽，不能靠用户去翻 meguru。

## 方面 3：识别缺失的关键信息

### 缺失 3.1：Fallback 编号表（最关键）

如上 2.5。AI 拿到「走Fallback #2/#7/#10」无定义可查。**必补一张 Fallback 编号对照表**（至少 #2 时效、#7 引用堆叠、#10 危机 三项，因为这是本 skill 实际引用的编号）。

### 缺失 3.2：段落长度上限 + 长对话校准

如上 2.2。无段长上限 → 易冗长；无周期校准 → 长对话漂移。同类 skill 都有，本 skill 应补齐。

### 缺失 3.3：严重危机的具体处理协议

Fallback #10 被引用为「严重危机」出口，但即便补了编号表，**严重危机本身需要具体协议**（用户表露自伤/绝望时，智代子该做什么、不能做什么）。skill 在「不擅长」里列了物理接触/恐怖话题，但**没有写遇到用户心理危机时的行为**。这是 AI 最容易「不知道该怎么处理」的场景，且风险最高。建议在 Fallback #10 定义里附 1-2 句行为指引（如：停止扮演腔→明确关心→建议求助专业资源，不在角色内「逞强接住」危机）。

### 缺失 3.4：研究预算——已有 ✅

Step 2 有「每个问题最多搜索 2-3 轮…预算用尽→『一緒に調べませんか？』收束」，可执行。✅ 无需改。

### 缺失 3.5：对话长度上限——部分有

有「4段内给出行动/出口」硬规则，等于隐式 4 段上限，但**没有字数上限**（meguru 单段≤120字、asahi≤150字）。配合 3.2 一并解决。

| 特征 | 限制 |
|------|------|
| えへへ | 每段≤2 处（143 条语料仅 10 次≈7%，是稀缺润滑笑，不是每段必出） |
